## 1. What is monitored

| Area | Signals | Source |
|---|---|---|
| API availability and load | scrape `up`, requests in flight, process restarts, RED (rate / errors / p95) per route, DB pool | API `/metrics` listener (`SUTRA_METRICS=true`, `SUTRA_METRICS_ADDR`, default `:9464`) |
| PostgreSQL | up, connections vs `max_connections`, replication lag, long transactions, slow statements (`pg_stat_statements`), dead-row bloat, deadlocks, database size | `postgres_exporter` with the read-only `sutra_monitor` role (`deploy/monitoring/postgres/monitor-role.sql`) |
| Backups and WAL | last backup run success, last success age (24 h RPO + 2 h grace), duration, size; WAL archive failures and archive age | backup wrapper → node_exporter textfile collector; `pg_stat_archiver` |
| Security | failed / throttled sign-ins, lockouts, MFA failures, privilege changes, cross-tenant denials, webhook and checkout signature failures | `sutra_security_events_total{event}` from `sutra_kernel::signal` (hooks in auth, identity, finance webhook / checkout, RLS-scope guard) |
| Queues and jobs | outbox publish failures and backlog, NATS / JetStream health and consumer lag, scheduled job outcomes, idp-sync backlog (`sutra_idp_sync_links{status}`), stale gateway payments (`sutra_gateway_payments_open_stale`) | API metrics (system DB context, counts every tenant under RLS), NATS exporter |
| Integrations | Razorpay, S3 / MinIO, Keycloak admin API, SMTP call outcomes (ok / error / timeout); `/health/ready` probes document storage with a 1.5 s budget and counts a hang as an S3 timeout (DEF-P2-MON-001) | `sutra_integration_calls_total{integration,outcome}` |
| Host | node up, disk space (low / critical / predicted full in 24 h), CPU, memory | node_exporter |
| Monitoring itself | always-firing watchdog to a dead-man's switch, rule evaluation failures, notification delivery failures, Alertmanager / Grafana up | Prometheus / Alertmanager self-metrics |
| Audit chain, error rate, latency, outbox backlog (slice 9A, unchanged) | 7 alerts | `deploy/observability/alerts/sutra.rules.yaml` — runbooks in [`docs/runbooks/observability.md`](../runbooks/observability.md) |

### Where it lives

`sutraerp/deploy/monitoring/` (generated by `gen.py`; never edit the YAML/JSON by hand — edit `gen.py`
and run `python3 gen.py`, CI fails when they are out of sync):

- `compose.yaml` — Prometheus v3.13.4, Alertmanager v0.34.1, Grafana 12.4.13, postgres_exporter v0.20.1,
  node_exporter v1.12.1 (+ textfile dir), NATS exporter 0.20.2. Every UI binds to `127.0.0.1` only:
  publish through the site's reverse proxy / VPN, never directly.
- `prometheus/` — `prometheus.yml` (scrape 15 s, evaluation 30 s), file-SD targets
  (`targets/sutra-api.yml`, `targets/node.yml`), `rules/sutra-onprem.rules.yaml` (47 alerts, 8 groups),
  `rules/tests/` (promtool unit tests). The 9A rules are loaded alongside.
- `alertmanager/render.py` + `templates/sutra.tmpl` — renders `alertmanager.yml` from
  `/etc/sutraerp/monitoring.env`; routes: `SutraWatchdog` → dead-man (repeat 5 m), `critical` →
  e-mail + chat + SMS (repeat 1 h), `warning` → e-mail + chat (repeat 4 h); critical inhibits the matching
  warning. `--require-delivery` refuses to render a config that delivers nowhere.
- `grafana/` — provisioned Prometheus datasource and dashboards.
- `textfile/sutra-backup-metrics.sh`, `systemd/sutra-backup.{service,timer}` — backup metrics.
- `monitoring.env.example` — every setting, with the delivery keys that are BLOCKED_EXTERNAL.
- `drill/` + `compose.drill.yaml` — the fault-injection drill (CI only).

> **Backup jobs must write metrics.** Whatever runs the backup (the backup worker's script, `pg_dump`,
> pgBackRest, the Kubernetes CronJob's shell) must be wrapped:
> `deploy/monitoring/textfile/sutra-backup-metrics.sh --kind <logical|base|...> --dir /var/lib/sutraerp/node-exporter --size-of <backup file> -- <backup command>`.
> The wrapper runs the command unchanged, returns its exit code and atomically rewrites
> `sutra_backup_<kind>.prom`. Without it SutraBackupMissing fires after 2 h and SutraBackupFailed /
> SutraBackupStale can never fire. See [BACKUP_RESTORE_REPORT.md](BACKUP_RESTORE_REPORT.md) for the backup
> procedure itself.

## 4. Measured alert latency (fault-injection drill)

GitHub-hosted runner (AMD EPYC 7763 64-Core Processor, 4 vCPU, 15 GiB) — NOT college hardware. Run [38916609615](https://github.com/Varad1614/ERP_hark_2/actions/runs/38916609615) (job 117025881221), commit `f0bcccdf`.
Stack (10 containers) up and healthy in **20 s**; targets all `up`; every rule `health=ok`; all 24 required
metric families present (API, PostgreSQL, node, NATS, backup textfile).

The drill copies the rules with every `for:` capped at 20 s and evaluation at 10 s
(`drill/ci-rules.py`) so it finishes in minutes; the **expressions are the production ones**, and the
production `for:` durations are proven separately by the promtool unit tests. "Seconds" = from the fault
being injected until the alert was firing in Prometheus / active in Alertmanager (polled every 2 s).

| Fault injected (real) | Alert | Prod `for` | Prometheus firing | Alertmanager active | Delivered |
|---|---|---|---|---|---|
| — (heartbeat) | SutraWatchdog | — | 0 s | 0 s | dead-man webhook `/deadman` ✔ |
| 6 payment webhooks with a wrong `X-Razorpay-Signature` (API answered 401 each) | SutraWebhookSignatureFailures | — | **6 s** | 6 s | e-mail in Mailpit ✔ |
| MinIO frozen with SIGSTOP while `/health/ready` is polled (S3 requests hang) | SutraS3Errors | 5m (drill 20 s) | **56 s** | 56 s | e-mail ✔ |
| WAL archive destination made read-only, `pg_switch_wal()` (archiver failed=3) | SutraWalArchiveFailing | — | **13 s** | 13 s | e-mail + SMS webhook ✔ |
| `docker compose stop postgres` | SutraPostgresDown | 1m (drill 20 s) | **35 s** | 35 s | e-mail + SMS webhook `/sms` ✔ |
| scheduled backup run while PostgreSQL is down (pg_dump fails, wrapper writes `last_run_success 0`) | SutraBackupFailed | — | **35 s** | 35 s | e-mail + SMS ✔ |
| API readiness while PostgreSQL is down | — | — | `/health/ready` → **503** | — | — |
| Recovery: PostgreSQL started, backup re-run | SutraBackupFailed, SutraPostgresDown | — | resolved | resolved | resolved notifications |

Delivered during the drill: **7 e-mails** (Mailpit standing in for the college SMTP relay) and **11
webhook posts** (chat, SMS adapter, dead-man). Monitoring stack footprint at the end of the drill:
Grafana 129 MiB, Prometheus 104 MiB, PostgreSQL 54 MiB, postgres_exporter 25 MiB, Alertmanager 20 MiB,
the rest < 17 MiB each; CPU < 0.4 % per container (runner numbers).

Earlier attempts of the same drill measured SutraWebhookSignatureFailures 12 s and SutraS3Errors 45 s
(run 38914782594, which then failed at the WAL fault — fixed in `f0bcccdf`: the archive_command is set on
the PostgreSQL command line, which outranks `ALTER SYSTEM`, so the drill now makes the archive directory
read-only instead). The spread (6–12 s, 45–56 s) is scrape / evaluation phase.

**Expected latency in production** (upper bound, from the configuration, not measured): `for` + up to
30 s evaluation + up to 15 s scrape + 30 s Alertmanager `group_wait`. E.g. SutraPostgresDown ≤ 1m + 75 s
≈ 2¼ min; SutraS3Errors ≤ 5m + 75 s; SutraWebhookSignatureFailures / SutraWalArchiveFailing /
SutraBackupFailed ≤ 75 s. Measure these again on the college server (§10).

## 5. Installation support runbook

Install the monitoring stack on the monitoring host (may be the ERP host for a single-server college).
This is exactly what the drill does on the runner, from the release bundle — not a dev checkout.

```bash
# 1. Unpack the bundle (deploy/monitoring + deploy/observability/{alerts,dashboards}).
sudo mkdir -p /opt/sutraerp /etc/sutraerp /var/lib/sutraerp/node-exporter
sudo tar xzf sutraerp-monitoring-bundle.tgz -C /opt/sutraerp
cd /opt/sutraerp/deploy/monitoring

# 2. Read-only monitoring role in PostgreSQL (once), and pg_stat_statements:
#    shared_preload_libraries = 'pg_stat_statements' in postgresql.conf (restart), then
sudo -u postgres psql -d sutra -f postgres/monitor-role.sql   # set its password afterwards
#    WAL archiving must be on: archive_mode = on, archive_command = '...', archive_timeout = 900

# 3. Settings
sudo cp monitoring.env.example /etc/sutraerp/monitoring.env && sudo chmod 600 /etc/sutraerp/monitoring.env
sudoedit /etc/sutraerp/monitoring.env        # Grafana password, PG DSN, NATS URL, SMTP / chat / SMS / dead-man
python3 alertmanager/render.py --env /etc/sutraerp/monitoring.env --out alertmanager/alertmanager.yml --require-delivery

# 4. API metrics: in the API environment SUTRA_METRICS=true, SUTRA_METRICS_ADDR=0.0.0.0:9464,
#    then point prometheus/targets/sutra-api.yml at the API host(s); restart the API.

# 5. Start and verify
docker compose --env-file /etc/sutraerp/monitoring.env -f compose.yaml up -d --wait
curl -s localhost:9090/api/v1/targets | jq -r '.data.activeTargets[] | "\(.labels.job) \(.health)"'   # all "up"
curl -s localhost:9090/api/v1/rules | jq '[.data.groups[].rules[] | select(.health != "ok")] | length'  # 0
curl -s localhost:9093/api/v2/alerts | jq -r '.[].labels.alertname'                                    # SutraWatchdog
```

**Common installation problems**

| Symptom | Cause | Fix |
|---|---|---|
| `render.py` exits "no alert delivery configured" | `--require-delivery` and every receiver key empty | fill at least SMTP or chat (production: all of them) |
| target `sutra-api` down | metrics not enabled / firewall / wrong host in `targets/sutra-api.yml` | `SUTRA_METRICS=true`, open 9464 from the monitoring host only |
| target `postgres` up but `pg_up 0` | DSN / password / `pg_hba.conf` | connect with `psql "$SUTRA_MON_PG_DSN"` from the monitoring host |
| no `pg_stat_statements_*` | extension not preloaded | `shared_preload_libraries`, restart, `CREATE EXTENSION pg_stat_statements` (in monitor-role.sql) |
| SutraBackupMissing after 2 h | backup not wrapped, or textfile dir differs between the backup host and node_exporter | §1 note; same `SUTRA_MON_TEXTFILE_DIR` |
| Grafana empty panels | datasource uid changed / Prometheus down | provisioned uid must stay `prometheus` |
| `host.docker.internal` unresolved (Linux) | older Docker | compose adds `extra_hosts: host-gateway`; Docker ≥ 20.10 |

## 6. Alert runbooks

Format per alert: what it means → **Check** → **Fix**. Severity levels and roles are in §8. Commands
assume the on-prem layout (`/opt/sutraerp`, systemd units, `psql -U sutra sutra`); on Kubernetes use the
equivalent `kubectl` commands from [docs/runbooks/deploy.md](../runbooks/deploy.md).

### SutraApiDown

*API · critical · for 2m* — Prometheus cannot scrape the API metrics listener for 2 minutes: the API process is down, restarting in a loop, or the metrics port is blocked.

- **Check:** `systemctl status sutra-api` (or `docker ps` / `kubectl get pods`); `curl -s localhost:8080/health/live`; `curl -s localhost:9464/metrics | head`; `journalctl -u sutra-api -n 200`.
- **Fix:** Process dead → start it and read the last log lines for the refusal (production refuses to start on a missing secret or mock adapter — fix the env, never switch the check off). Running but metrics unreachable → `SUTRA_METRICS=true`, `SUTRA_METRICS_ADDR`, host firewall between Prometheus and :9464. Sev-1 if users cannot reach the ERP.

### SutraApiSaturated

*API · warning · for 5m* — More than 100 requests have been in flight for 5 minutes: the API or the database is not keeping up (check latency, the DB pool and host CPU).

- **Check:** API RED dashboard (`sutra-api-red`): latency and in-flight by route; `SutraDbPoolSaturated` / `SutraPostgresSlowQueries`; host CPU.
- **Fix:** Slow database → treat the PostgreSQL alert first. One hot route (bulk import, report) → let it finish or cancel the job; otherwise add an API replica / raise the DB pool within `max_connections`.

### SutraApiRestarting

*API · warning* — The API process start time changed more than twice in 30 minutes (crash loop, OOM kill or failing health checks).

- **Check:** `journalctl -u sutra-api --since -1h | grep -iE 'panic|killed|refus'`; `dmesg -T | grep -i oom`.
- **Fix:** OOM → raise the memory limit or find the request; panic → capture the log, open a defect, roll back to the previous release (docs/runbooks/deploy.md §6) if it repeats.

### SutraPostgresDown

*PostgreSQL · critical · for 1m* — postgres_exporter cannot connect to PostgreSQL for 1 minute. The API answers 503 on /health/ready and every write fails.

- **Check:** `systemctl status postgresql` / `docker compose ps postgres`; `pg_isready -h <host> -U sutra`; PostgreSQL log (`journalctl -u postgresql -n 200`); disk space (`df -h` on the data and WAL volumes).
- **Fix:** Disk full → free space on the WAL volume (never delete files in pg_wal by hand; fix archiving, see SutraWalArchiveFailing). Crash → restart and watch the log for recovery. Data directory damaged → disaster recovery (§8.2). Sev-1: every write fails and `/health/ready` answers 503 (measured in the drill).

### SutraPostgresExporterDown

*PostgreSQL · warning · for 5m* — Prometheus cannot scrape postgres_exporter for 5 minutes; database alerts are blind.

- **Check:** `docker compose ps postgres-exporter`; `docker compose logs postgres-exporter`.
- **Fix:** Usually the `sutra_monitor` password or `SUTRA_MON_PG_DSN` changed → re-apply `postgres/monitor-role.sql` / fix the DSN and `docker compose up -d postgres-exporter`. While it is down every database alert is blind.

### SutraPostgresConnectionsHigh

*PostgreSQL · warning · for 10m* — More than 80 % of max_connections are in use for 10 minutes; new connections will soon be refused.

- **Check:** `SELECT usename, application_name, state, count(*) FROM pg_stat_activity GROUP BY 1,2,3 ORDER BY 4 DESC;`
- **Fix:** Many `idle in transaction` → find the client (see SutraPostgresLongTransaction). Legitimate load → lower API pool size per replica or raise `max_connections` (needs a restart and RAM).

### SutraPostgresReplicationLag

*PostgreSQL · warning · for 5m* — The standby replays WAL more than 5 minutes behind the primary; a failover now would lose recent writes.

- **Check:** On the primary: `SELECT client_addr, state, replay_lag FROM pg_stat_replication;` On the standby: disk / network.
- **Fix:** Network or standby I/O bound → fix it; do not fail over while lag is high unless the primary is gone (you lose the lag window).

### SutraPostgresLongTransaction

*PostgreSQL · warning · for 5m* — A transaction has been open for more than 10 minutes (slow query, stuck job or idle in transaction); it holds locks and blocks vacuum.

- **Check:** `SELECT pid, usename, state, now()-xact_start AS age, left(query,120) FROM pg_stat_activity WHERE xact_start < now()-interval '10 min' ORDER BY age DESC;`
- **Fix:** An ad-hoc session → ask its owner, then `SELECT pg_cancel_backend(pid)` (or `pg_terminate_backend`). A SutraERP job → check its run in the outbox/jobs dashboard and open a defect.

### SutraPostgresSlowQueries

*PostgreSQL · warning · for 15m* — A statement averaged more than 1 second per call over 10 minutes (pg_stat_statements); see the PostgreSQL dashboard's slowest statements.

- **Check:** PostgreSQL dashboard → slowest statements; `SELECT calls, mean_exec_time, left(query,120) FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;`
- **Fix:** `EXPLAIN (ANALYZE, BUFFERS)` the statement; missing index → defect + migration (append-only). Stale statistics → `ANALYZE <table>`.

### SutraPostgresTableBloat

*PostgreSQL · warning · for 1h* — A table has over 100,000 dead rows and more than 20 % of its rows are dead for an hour: autovacuum is not keeping up (long transactions, vacuum settings).

- **Check:** `SELECT relname, n_dead_tup, n_live_tup, last_autovacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;`
- **Fix:** Clear the long transaction holding the xmin horizon first, then `VACUUM (VERBOSE, ANALYZE) <table>`. Recurring → tune per-table autovacuum settings.

### SutraPostgresDeadlocks

*PostgreSQL · warning* — More than 5 deadlocks in 15 minutes; requests are being aborted and retried.

- **Check:** PostgreSQL log lines `deadlock detected` (they include both statements).
- **Fix:** Note the statements and the module; open a defect (lock order). Occasional retries are harmless; a burst during an import → pause the import.

### SutraBackupFailed

*Backups / WAL · critical* — The most recent backup run (sutra-backup-metrics.sh) exited non-zero. The previous good backup is still the restore point; RPO is at risk.

- **Check:** `systemctl status sutra-backup.service`; `journalctl -u sutra-backup -n 200`; `cat /var/lib/sutraerp/node-exporter/sutra_backup_*.prom`.
- **Fix:** Fix the cause (PostgreSQL down, target disk full, credentials) and run `systemctl start sutra-backup.service`; the alert clears when the run succeeds (drill: recovery step). The previous good backup stays the restore point; record the gap against the 24 h RPO.

### SutraBackupStale

*Backups / WAL · critical* — The newest successful backup is older than 26 hours (daily schedule + 2 h grace): the 24 h RPO is breached. The backup timer stopped or every run fails.

- **Check:** `systemctl list-timers sutra-backup.timer`; last success: `sutra_backup_last_success_timestamp_seconds` on the host & backups dashboard.
- **Fix:** Timer disabled → `systemctl enable --now sutra-backup.timer`; every run failing → SutraBackupFailed steps. Take a manual backup now; the RPO is breached (Sev-2).

### SutraBackupMissing

*Backups / WAL · warning · for 2h* — Prometheus has no backup metrics for 2 hours: the backup has never run with sutra-backup-metrics.sh, or node_exporter's textfile directory is not mounted.

- **Check:** `ls -l /var/lib/sutraerp/node-exporter/`; `curl -s localhost:9100/metrics | grep sutra_backup` from the monitoring host.
- **Fix:** The backup job must run through `deploy/monitoring/textfile/sutra-backup-metrics.sh` and node_exporter must mount the same directory (`SUTRA_MON_TEXTFILE_DIR`). Wire the job (example units in `deploy/monitoring/systemd/`).

### SutraWalArchiveFailing

*Backups / WAL · critical* — archive_command failed in the last 15 minutes: point-in-time recovery has a gap and pg_wal grows until the disk fills.

- **Check:** `SELECT archived_count, failed_count, last_failed_wal, last_failed_time FROM pg_stat_archiver;` PostgreSQL log `archive command failed`; free space and permissions on the archive destination.
- **Fix:** Fix the destination (mount, permissions, space, object-store credentials). PostgreSQL retries the same segment automatically; `failed_count` stops rising and the alert clears 15 min later. Until then PITR has a gap and pg_wal grows — watch disk. (Drill: archive dir made read-only → fired in 13 s.)

### SutraWalArchiveStale

*Backups / WAL · warning · for 15m* — No WAL segment has been archived for 2 hours although archive_timeout forces one at least every 15 minutes: archiving is stuck.

- **Check:** `SELECT last_archived_wal, last_archived_time FROM pg_stat_archiver;` `SHOW archive_mode; SHOW archive_timeout;`
- **Fix:** archive_mode off after a config change → restore it (restart). archive_command hanging (network mount) → fix the mount.

### SutraLoginFailureSpike

*Security · warning* — Failed sign-ins spiked (password spraying, a broken integration, or many users locked out). Check the auth logs by login and source address.

- **Check:** Security dashboard (`sutra-security`); API log `login_failed` events by login and source address.
- **Fix:** Spraying from a few addresses → block them at the reverse proxy / firewall; an integration with an expired password → fix it. If accounts were compromised → §8.1 security incident.

### SutraLoginThrottleSpike

*Security · warning* — Sign-ins are being refused by the lockout throttle: brute force against specific accounts.

- **Check:** Security dashboard; which logins are throttled.
- **Fix:** Targeted brute force → block the source; contact the account owners; consider forcing MFA for those accounts.

### SutraAccountLockouts

*Security · warning* — Several logins were locked after repeated failures in a short time.

- **Check:** Security dashboard; audit trail for the locked accounts.
- **Fix:** Verify with the users (help desk) before unlocking; a wave of lockouts from one source is an attack → §8.1.

### SutraMfaFailureSpike

*Security · warning* — Second-factor codes / passkeys are being rejected in bulk: guessing against stolen passwords or a clock problem on the server (TOTP).

- **Check:** `timedatectl` on the API host (TOTP needs correct time); security dashboard by user.
- **Fix:** Clock drift → enable NTP (`timedatectl set-ntp true`). Failures concentrated on accounts whose password is right → passwords are compromised → §8.1, reset those passwords.

### SutraPrivilegeChanges

*Security · warning* — Roles were granted / revoked more than 10 times in an hour. Verify against approved requests in the audit trail (platform.identity.*).

- **Check:** Audit trail `platform.identity.*` events for the last hour; compare with approved requests (APPROVAL_CONTROL_MATRIX.md).
- **Fix:** All approved (e.g. term start) → acknowledge. Any unapproved grant → revoke it, suspend the actor, §8.1.

### SutraCrossTenantDenied

*Security · warning* — A request named a tenant or institution outside its session scope and was refused (403). Normal clients never do this: treat as probing until explained.

- **Check:** API log for the denied requests (user, tenant, route).
- **Fix:** A UI bug → defect. A user crafting requests → suspend the account, preserve logs, §8.1. RLS denied it; confirm no data left (audit trail).

### SutraWebhookSignatureFailures

*Security · warning* — At least 3 payment-gateway webhooks in 10 minutes had a missing or wrong signature: forged callbacks, or SUTRA_PAYMENT_WEBHOOK_SECRET differs from the gateway dashboard.

- **Check:** Finance webhook log lines (401); compare `SUTRA_PAYMENT_WEBHOOK_SECRET` with the gateway dashboard's webhook secret; source addresses.
- **Fix:** Secret rotated on one side only → set the same secret and restart; the gateway re-delivers. Forged callbacks from unknown addresses → block them, §8.1 (no payment is marked paid without a valid signature). (Drill: 6 bad signatures → fired in 6 s, e-mail delivered.)

### SutraCheckoutSignatureFailures

*Security · warning* — At least 5 checkout callbacks in 30 minutes failed signature verification (tampering or a wrong key secret).

- **Check:** Finance log for checkout verification failures; key id / secret in the env.
- **Fix:** Wrong key secret after rotation → fix and restart. Tampering → §8.1; affected payments remain pending and are resolved by the recovery job.

### SutraOutboxPublishFailing

*Queues / jobs / retry backlogs · warning · for 15m* — More than 10 outbox publish attempts failed in 15 minutes (NATS down or rejecting).

- **Check:** `sutra-outbox-jobs` dashboard; `nats server check connection` / NATS log.
- **Fix:** NATS down → SutraNatsDown steps; events stay in the outbox and are published when NATS returns (nothing is lost).

### SutraNatsDown

*Queues / jobs / retry backlogs · critical · for 2m* — The NATS exporter cannot be scraped or NATS is down for 2 minutes: events queue up in the outbox.

- **Check:** `systemctl status nats-server` / `docker compose ps nats`; `curl -s localhost:8222/healthz`.
- **Fix:** Restart NATS; check the JetStream storage disk. Outbox drains automatically afterwards.

### SutraJetStreamConsumerLag

*Queues / jobs / retry backlogs · warning · for 15m* — A JetStream consumer has more than 1000 pending messages for 15 minutes; a consumer is down or too slow.

- **Check:** `nats consumer report <stream>`; which consumer is behind.
- **Fix:** Consumer down → restart the service that owns it; slow → scale it. Pending messages are kept by JetStream.

### SutraIdpSyncFailing

*Queues / jobs / retry backlogs · warning · for 30m* — Identity links have stayed in sync_status=failed for 30 minutes: Keycloak is unreachable or refuses the admin client; the idp-sync job retries with back-off.

- **Check:** Queues & integrations dashboard (`sutra_idp_sync_links`); Keycloak health; `SutraKeycloakAdminErrors`.
- **Fix:** Restore Keycloak / the admin client credentials (`SUTRA_IDP_CLIENT_ID` / `SUTRA_IDP_CLIENT_SECRET`); the idp-sync job retries with back-off and the failed count drains.

### SutraIdpSyncConflict

*Queues / jobs / retry backlogs · warning · for 1h* — An identity link is in sync_status=conflict (an IdP account owned elsewhere): it is not retried automatically.

- **Check:** Identity admin screen → links in conflict (an IdP account already owned by another person).
- **Fix:** An administrator resolves each conflict (link to the right person or rename in Keycloak). Not retried automatically by design.

### SutraIdpSyncBacklog

*Queues / jobs / retry backlogs · warning · for 30m* — The idp-sync job is not draining its queue (job disabled, slow IdP, or a bulk import).

- **Check:** Is the idp-sync job enabled and running (`sutra_job_runs_total{job="idp-sync"}`)? Was there a bulk import?
- **Fix:** After a bulk import a temporary backlog is expected — watch it drain. Not draining → job disabled or Keycloak slow (see SutraKeycloakAdminErrors).

### SutraPaymentRecoveryStale

*Queues / jobs / retry backlogs · warning · for 1h* — Gateway payments stayed initiated / pending for over an hour and the recovery job has not resolved them (gateway API errors, or the job is off).

- **Check:** Queues & integrations dashboard (`sutra_gateway_payments_open_stale`); `SutraRazorpayErrors`; recovery job runs.
- **Fix:** Gateway API down → wait / contact Razorpay; job disabled → enable it. Do NOT mark payments paid by hand; the recovery job reconciles against the gateway.

### SutraIdpSyncJobErrors

*Queues / jobs / retry backlogs · warning* — The idp-sync scheduled job failed at least twice in 30 minutes (each run retries the backlog; persistent failure means its dependency is down).

- **Check:** API log for `idp-sync` job errors.
- **Fix:** Same as SutraIdpSyncFailing; persistent errors with Keycloak healthy → defect.

### SutraPaymentRecoveryJobErrors

*Queues / jobs / retry backlogs · warning* — The payment_gateway_recovery scheduled job failed at least twice in 30 minutes (each run retries the backlog; persistent failure means its dependency is down).

- **Check:** API log for `payment_gateway_recovery` job errors.
- **Fix:** Gateway credentials / reachability (SutraRazorpayErrors); persistent errors with the gateway healthy → defect.

### SutraRazorpayErrors

*Integrations · warning · for 5m* — More than 25 % of Razorpay API calls (at least 5) failed or timed out over 10 minutes.

- **Check:** Queues & integrations dashboard (calls by outcome); Razorpay status page; outbound HTTPS from the API host.
- **Fix:** Provider outage → inform the finance office (online fee payment degraded; pending payments are recovered later). Auth errors → key rotated; fix `SUTRA_RAZORPAY_*` and restart.

### SutraS3Errors

*Integrations · warning · for 5m* — More than 25 % of Object storage (S3 / MinIO) calls (at least 5) failed or timed out over 10 minutes.

- **Check:** `mc admin info <alias>` / MinIO log; free space on the MinIO volume; `curl -s localhost:8080/health/ready`.
- **Fix:** Restore object storage (start, free space, credentials). Document upload/download fail meanwhile; readiness reports the timeout (DEF-P2-MON-001). (Drill: MinIO frozen → fired in 56 s with `for` capped at 20 s.)

### SutraKeycloakAdminErrors

*Integrations · warning · for 5m* — More than 25 % of Keycloak admin API calls (at least 5) failed or timed out over 10 minutes.

- **Check:** Keycloak health (`/health/ready` on its management port); admin client credentials.
- **Fix:** Restore Keycloak / rotate the admin client secret in the env; idp-sync then catches up.

### SutraSmtpErrors

*Integrations · warning · for 5m* — More than 25 % of SMTP relay calls (at least 5) failed or timed out over 10 minutes.

- **Check:** API log for SMTP errors; `openssl s_client -starttls smtp -connect <relay>:587` from the API host.
- **Fix:** Relay down / credentials changed → fix with the college mail admin. Notification mails are retried by the job; if the same relay carries alert e-mail, also expect SutraAlertNotificationsFailing.

### SutraHostDown

*Host · critical · for 2m* — node_exporter cannot be scraped for 2 minutes: the host is down or the exporter stopped.

- **Check:** Ping / console of the host; `systemctl status prometheus-node-exporter` or `docker compose ps node-exporter`.
- **Fix:** Host down → Sev-1 if it runs the API or PostgreSQL; follow §8.2 if it does not come back. Exporter only → restart it.

### SutraHostDiskSpaceLow

*Host · warning · for 10m* — A filesystem has less than 15 % free space (PostgreSQL data, WAL archive or backups).

- **Check:** `df -h`; `du -xh --max-depth=2 /var/lib | sort -h | tail`; backup retention; WAL archive size.
- **Fix:** Apply backup / archive retention, remove old release bundles and logs. Never delete PostgreSQL data or pg_wal files by hand. Plan more disk.

### SutraHostDiskSpaceCritical

*Host · critical · for 5m* — A filesystem is almost full; PostgreSQL stops accepting writes when its disk is full.

- **Check:** As SutraHostDiskSpaceLow — now urgent (Sev-1 if it is the PostgreSQL volume).
- **Fix:** Free space immediately (old backups already copied off-host, logs, docker images: `docker image prune`). If PostgreSQL already stopped, free space and start it; check SutraWalArchiveFailing.

### SutraHostDiskFillingUp

*Host · warning · for 1h* — At the growth rate of the last 6 hours a filesystem runs out of space within a day.

- **Check:** Host & backups dashboard: which mount, growth since when.
- **Fix:** Find the writer (runaway log, failed archiving keeping pg_wal, an import). Fix before SutraHostDiskSpaceCritical.

### SutraHostCpuHigh

*Host · warning · for 15m* — The host's CPUs have been more than 90 % busy for 15 minutes.

- **Check:** `top` / `pidstat 5`; API RED dashboard; PostgreSQL slow statements.
- **Fix:** Expected peak (fee deadline, results day) → ride it out / scale; a runaway query → cancel it.

### SutraHostMemoryLow

*Host · warning · for 10m* — Available memory stayed below 10 % for 10 minutes; the kernel may OOM-kill PostgreSQL or the API.

- **Check:** `free -m`; `ps aux --sort=-rss | head`; `dmesg -T | grep -i oom`.
- **Fix:** Reduce `shared_buffers`/`work_mem` or API replicas to fit the host; add RAM. An OOM-killed PostgreSQL restarts with crash recovery.

### SutraWatchdog

*Monitoring itself · none* — Always firing. Route it to a dead-man's switch: if it stops arriving, Prometheus or Alertmanager is down.

- **Check:** Not an incident. The dead-man service must receive it every few minutes (route `deadman`, repeat 5 m).
- **Fix:** If the dead-man service pages that the heartbeat stopped: Prometheus, Alertmanager or the monitoring host is down — `docker compose ps` in `/opt/sutraerp/deploy/monitoring` and restart.

### SutraRuleEvaluationFailures

*Monitoring itself · warning* — A rule group fails to evaluate; some alerts cannot fire.

- **Check:** Prometheus UI → Status → Rules (unhealthy rules show the error).
- **Fix:** Usually a rule file edited by hand. Re-generate with `python3 gen.py`, check with promtool, reload (`curl -X POST localhost:9090/-/reload`).

### SutraAlertNotificationsFailing

*Monitoring itself · warning* — Alertmanager failed to deliver notifications (SMTP relay, chat or SMS webhook unreachable or refusing); alerts are not reaching people.

- **Check:** `docker compose logs alertmanager | grep -i notify`; reachability of the SMTP relay / chat / SMS URLs from the monitoring host.
- **Fix:** Fix the receiver (credentials, firewall, URL) in `/etc/sutraerp/monitoring.env`, re-render (`python3 alertmanager/render.py --env /etc/sutraerp/monitoring.env --out alertmanager/alertmanager.yml --require-delivery`) and restart Alertmanager. Until fixed, watch Grafana / the Alertmanager UI by hand.

### SutraScrapeTargetDown

*Monitoring itself · warning · for 5m* — Alertmanager or Grafana has not been scrapeable for 5 minutes.

- **Check:** `docker compose ps` in `/opt/sutraerp/deploy/monitoring`.
- **Fix:** `docker compose up -d alertmanager grafana`; check the container log for config errors.

## 8. Incident response

### Severity

| Sev | Definition | Examples | Response | Update cadence |
|---|---|---|---|---|
| **Sev-1** | ERP unavailable or data at risk for everyone | SutraApiDown, SutraPostgresDown, disk critical on the DB volume, suspected breach / data leak, audit chain broken | on-call acknowledges ≤ 15 min (24×7), incident lead named immediately | every 30 min |
| **Sev-2** | Major function degraded, or a safety net is gone | payments failing, backups stale (RPO breached), WAL archiving failing, sign-in failing for a group | acknowledge ≤ 1 h in working hours (≤ 4 h otherwise) | every 2 h |
| **Sev-3** | Minor / one user / has a workaround | one slow report, a conflict in idp-sync, warning-level host alerts | next working day | at resolution |

Critical alerts start at Sev-2 at least; the on-call raises to Sev-1 by the definition above.

### Roles

| Role | Who (fill at go-live) | Does |
|---|---|---|
| On-call engineer | college IT / vendor support rota | acknowledges, diagnoses with §6–§7, fixes or escalates |
| Incident lead (Sev-1/2) | IT head / vendor lead | owns the incident, decides rollback / failover / DR, approves communications |
| Communications | ERP coordinator (registrar's office) | informs users and management using the templates below |
| DBA / infrastructure | college DBA / sysadmin | PostgreSQL, storage, network, restores |
| Security officer | college CISO / designated person | §8.1 security incidents, legal / CERT-In reporting |
| Vendor escalation | SutraERP maintainers | code defects, hotfix releases |

Contacts (phone, e-mail, deputy) are a go-live item — record them in the ops binder and in
`monitoring.env` receivers; the drill proves routing, not people.

### Flow

1. **Detect** — alert (e-mail / chat / SMS) or user report. Acknowledge in the chat channel
   ("ack SutraPostgresDown — <name>") and in Alertmanager (silence only once someone owns it, with a comment
   and an expiry).
2. **Triage** — assign Sev; Sev-1/2: name the incident lead, open an incident note (timeline in IST).
3. **Mitigate first** — restore service (restart, failover, roll back the release, block an attacker)
   before root-causing. Do not delete data, WAL, audit rows or logs.
4. **Communicate** — at the cadence above. Templates:
   - *Start:* "SutraERP <function> is unavailable / degraded since <time IST>. We are working on it. Next update by <time>."
   - *Update:* "Cause identified: <plain words>. Expected restoration <time / unknown>. Workaround: <…>."
   - *Resolved:* "SutraERP <function> restored at <time IST>. Data entered between <t1> and <t2> <is safe / must be re-entered: …>."
5. **Verify** — the alert resolved (Alertmanager sends a resolved notification), dashboards normal,
   a user confirms.
6. **Post-mortem** (Sev-1 and Sev-2, within 5 working days, blameless): summary, impact (users, duration,
   data), timeline, root cause, what went well / badly, actions with owners and dates (added to
   DEFECT_REGISTER.md when it is a code defect), whether an alert or runbook was missing — and then add or
   fix it in `deploy/monitoring/gen.py` with a promtool test.

### 8.1 Security incident

Triggers: SutraCrossTenantDenied, SutraPrivilegeChanges (unapproved), SutraLoginFailureSpike /
SutraMfaFailureSpike with successful sign-ins following, SutraWebhookSignatureFailures /
SutraCheckoutSignatureFailures from unknown sources, SutraAuditChainBroken, a report of a leaked
credential or data. Always at least Sev-2; Sev-1 if data of students/staff may have left the system.

1. **Contain**: suspend the affected accounts (identity admin), revoke sessions, block source addresses at
   the reverse proxy, rotate exposed secrets (OpenBao procedure in [docs/runbooks/security.md §4](../runbooks/security.md)) —
   webhook secret, Razorpay keys, S3 keys, IdP client secret, DB passwords as applicable.
2. **Preserve evidence**: do not restart or reimage before copying logs; export the audit trail for the
   window, API and proxy logs, `pg_stat_activity` snapshot; keep the audit chain (verify it — observability.md
   "Audit chain break response").
3. **Assess**: which tenant / records, read or changed (audit trail), how (credential, bug, insider).
4. **Notify**: security officer and management immediately; CERT-In within 6 hours of noticing a
   reportable incident (Indian CERT-In directions of 28 April 2022); affected persons and the data
   protection obligations under the DPDP Act 2023 as advised by the college's legal office.
5. **Eradicate and recover**: patch / fix, restore changed records from the audit trail or a backup
   (DR below), re-enable accounts after password reset + MFA.
6. **Post-mortem** as in §8, plus the security review in docs/runbooks/security.md.

### 8.2 Disaster recovery

Use when PostgreSQL data, the server or the object store is lost or corrupted (SutraPostgresDown that does
not recover, storage failure, ransomware, accidental mass deletion). Targets: **RPO 24 h, RTO 2 h**
(docs/runbooks/backup-dr.md).

1. Incident lead declares DR (Sev-1); freeze writes (put the proxy in maintenance mode).
2. Choose the restore point: the newest successful backup (`sutra_backup_last_success_timestamp_seconds`
   on the host & backups dashboard) plus WAL archive up to the last good moment for point-in-time recovery
   (if SutraWalArchiveFailing fired, PITR stops at the gap).
3. Restore following **[BACKUP_RESTORE_REPORT.md](BACKUP_RESTORE_REPORT.md)** (the tested procedure and
   measured restore times) and [docs/runbooks/backup-dr.md](../runbooks/backup-dr.md) "Restore (step by step)".
4. Verify: `/health/ready` 200, audit chain verifies, record counts / latest records match expectations,
   a finance and an academic user confirm.
5. Re-enable monitoring targets (new host → `targets/*.yml`), run a backup immediately (wrapped, so
   SutraBackupFailed / Stale clear), confirm WAL archiving (`pg_stat_archiver.archived_count` rising).
6. Communicate the data window that must be re-entered; post-mortem.
