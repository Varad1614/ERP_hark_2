# Capacity test report — 2,000-student college (Part 2 · Stage 5)

> **Every number in this report was measured on a GitHub-hosted runner — NOT college hardware.**
> The runner is a shared 4 vCPU / 15.6 GiB cloud VM. Load generator (k6) and the whole stack ran
> on the **same** host, so the load generator took CPU from the system under test. These figures
> show that the procedure works and where the stack breaks first. They are **not** a statement of
> what a college server can carry. The college-server run is **BLOCKED_EXTERNAL** (no server is
> available); see [To complete on the college server](#to-complete-on-the-college-server).

## Verdict

**Not passed on the runner.** Run 8 (38960531409, commit `ae097788`, the DEF-P2-CAP-007 fix; GitHub-hosted runner AMD EPYC
7763, 4 vCPU, 15.6 GiB — NOT college hardware) is **FAILED with 30 breaches** (run 7: 61). What changed and what did not:

- **Fee-deadline spike: fixed (DEF-P2-CAP-007 COMPLETED).** Errors 1.50 % → **0.08 %**, read p99 8.8 s → **551 ms**, write p99
  9.2 s → 498 ms, **zero** "database unavailable" / pool errors. The pool hold-and-wait in `/finance/me/charges` and the
  attendance register commands was the cause; the fix (`018d8766`) did not raise the pool size or touch a threshold.
- **Steady college day:** read p95 14 ms, sign-in p95 103 ms, errors 0.08 % — within the phase limits; the endpoint breaches in
  steady come from the office-desk 403s below.
- **Results-day spike: sign-in p95 5,011 ms vs the 5,000 ms limit** (run 7: 6.2 s). Keycloak peaked at **213 % CPU** of the
  4-vCPU host shared with k6 — a **capacity limit, not an API defect**. Sizing per Keycloak's guide (Production risks 2):
  ≈ 5 vCPU of steady Keycloak capacity, limit ≈ 12 vCPU, for ≈ 73 full password sign-ins/s.
- **19 breaches = one office desk answered 403 on all 344 of its requests** after a normal password + TOTP sign-in
  (`student.record`, `student.directory.search`, `finance.student-account`, `finance.payment.counter`, `finance.payments.list`,
  `finance.accounts.with-dues`, `exams.session.results`, `services.reports.library` across the three phases).
  **DEF-P2-CAP-009, OPEN — cause not verified** (the other desks with the same flow got 200).
- **8 latency breaches on heavy office reads**, p95 0.55–1.1 s against 0.5 / 0.8 s (`exams.paper.marks` GET 861–875 ms,
  `exams.session.results` 919–1,022 ms, `finance.accounts.with-dues` 554 ms, `exams.paper.marks.put` 1,136 ms) — product,
  whole-sheet / whole-list reads during the spikes; watch on college hardware, paginate if they repeat.
- `exams.paper.marks.put` errors (412 stale `If-Match`) — harness, as in runs 6 and 7.
- **DEF-P2-CAP-008 OPEN:** 93 heuristic hold-and-wait candidates (`docs/readiness/tools/hold-and-wait-scan.py`), all in office
  write paths, none on a student self-service route.
- DEF-P2-CAP-001…007 are fixed, each with a regression test, green in SutraERP CI.

**Run 9 — integrated head** (38961558841, `part2/int` @ `60471aab`, all Part 2 branches merged incl. the CAP-007 fix;
GitHub-hosted runner Intel Xeon Platinum 8573C, 4 vCPU, 15.6 GiB — NOT college hardware) is **FAILED with 3 breaches**, all the
harness 412 (stale `If-Match`) on `exams.paper.marks.put` in each phase. Everything else was inside the thresholds: errors 0.01 /
0.00 / 0.01 %, results sign-in p95 **3,983 ms** (Keycloak 242 % CPU), fees read p99 **163 ms**, no pool / 503 errors, no office
desk 403s. **DEF-P2-CAP-009 did not reproduce in run 9**, so it is intermittent and stays OPEN (cause unverified). The results
sign-in margin is a function of the runner's CPU model (run 8 AMD 5,011 ms vs run 9 Intel 8573C 3,983 ms), so Keycloak sizing
remains a production risk.

Do not take the college to production on the strength of this report. Before that: close DEF-P2-CAP-009 (and review
DEF-P2-CAP-008), size Keycloak, and get a clean run of this procedure on the college's own server with a separate load machine.

## What was run

The production-mode stack ran on one host: edge nginx (TLS, host network) → web nginx → API
(`SUTRA_ENV=production`, pool of 10 connections, the shipped default) → PostgreSQL 18 (TLS,
`pg_stat_statements`), Keycloak 26.7 (`start`, brute-force protection on), Flowable 8, NATS, Valkey
and MinIO (SSE-S3). Secrets came from a private CA and were random for each run.

**Seed (through the API, with real approvals):** Stage 4 imports created departments and programmes,
150 staff, and 2,000 students with guardians. The API provisioned 2,000 identities into Keycloak.
Then came 102 divisions with faculty, 2,000 term registrations plus 6,000 seats, the timetable,
6 weeks of attendance (1,224 sessions, 72,000 records in run 6), fees (2,000 charges, 1,600 counter
payments), 300 opening balances, the end-semester exam with results, an open internal assessment,
and one verified PDF per student.

**Load (`k6/college-day.js`, 21.5 minutes; each VU has its own source address):**

| Phase | Window | Users |
|---|---|---|
| steady | 0–10 min | 60 faculty + 40 office staff + 300 students visiting (sign-in → timetable, attendance, results, fees, documents → sign-out) |
| results | 10–15 min | results-day spike: 500 students signing in for results / grade cards |
| fees | 15–21.5 min | fee-deadline spike: 400 students signing in for accounts / charges / receipts / payment gateway |

Faculty and office staff ran throughout: they took attendance (create → start → mark → submit →
complete → finalise), entered marks, searched the directory, took counter payments and ran
reports.

## Run 5 — key numbers (GitHub-hosted runner, Intel Xeon Platinum 8370C, 4 vCPU, 15.6 GiB — NOT college hardware)

| | steady | results spike | fee spike |
|---|---|---|---|
| Throughput | 146 req/s | 364 req/s | 249 req/s |
| Errors | 0.18 % | 0.22 % | 0.14 % |
| Read p95 | 9 ms | 89 ms | 52 ms |
| Write p95 | 24 ms | 95 ms | 58 ms |
| Sign-in flow p95 (OIDC + Keycloak) | 87 ms | 3.3 s | 558 ms |

- **CPU, by container (one core = 100 %):** Keycloak peaked at 247 % (results spike). PostgreSQL
  peaked at 128 % and the API at 50 % or less. Web nginx reached 89 %, edge 13 %.
- **RAM:** about 3.2 GiB across all containers at peak (Keycloak 1.29 GiB, PostgreSQL 0.94 GiB,
  Flowable 0.42 GiB, MinIO 0.31 GiB, API 113 MiB).
- **PostgreSQL:** at most 34 connections, at most 4 active at once, no lock waiters, no
  deadlocks, cache hit ratio 0.99999.
- **Disk:** pgdata grew from 153 MiB to 774 MiB after the seed and 1,013 MiB after the load. The
  largest growth was outbox, idempotency keys, the audit log and attendance.
- **Errors in run 5:** 19–23 % of `academic.session.create` returned 409 ("already has a session
  at that date and time"). Several k6 VUs acted as the same teacher with the same slot counter:
  the API was right, the harness was wrong. In the results spike 1.76 % of `auth.session` failed:
  167 sign-ins of an account that was signing in from another VU at the same moment were refused
  by Keycloak's brute-force guard (`user_temporarily_disabled`). See Production risks. Both
  harness issues were fixed for run 6 (`22727f11`): visiting VUs own disjoint accounts, and each
  alias has its own session minute.

### DEF-P2-CAP-007 — API database pool stalls under the fee-deadline spike (FIXED in `018d8766`)

**Evidence (run 38939308465, artifact `capacity-evidence`):**

- The API log shows two windows in which **no request completed at all**. The first ran from
  load second ~1,015 to ~1,030 and the second from ~1,089 to ~1,110, both in the fees phase.
  At exact 5-second steps, 500–800 requests then failed together with 503 "database unavailable"
  after 5.0 s, which is `SUTRA_DB_ACQUIRE_TIMEOUT_SECS=5`. There were 1,926 × 503 in total and
  2,021 "acquired connection, but time to acquire exceeded slow threshold" warnings. Background
  jobs (`audit_seal`, `idp-sync`) failed with "pool timed out" at the same moments.
- **The system was idle during the stalls.** API CPU was 1 %, PostgreSQL 1 % and Keycloak 0.2 %
  (docker stats). In the PostgreSQL samples, all 10 `sutra_api` connections were open but
  **idle**, not active and not waiting on a lock, with 0 lock waiters.
- So all 10 pooled connections were checked out by API tasks that were not using them. The
  database was not busy, no lock was held, and CPU and RAM were free.

**Run 7 (38947132469, same signature on the Intel runner):** 226 "database unavailable" errors
in the API log (178 of them `session creation failed` and the rest `sign-in hook failed (profile
refresh)` on `GET /api/v1/auth/oidc/callback`), 4 "pool timed out" and 2,478 slow-acquire
warnings. Throughout the fees phase PostgreSQL showed at most 3 active connections, 0 waiting and
0 lock waiters, with the API's 10 connections open but idle. The **OIDC callback** (profile
refresh hook + session creation) is therefore the first path to instrument: it is where the
failures land, though that alone does not prove it holds the extra connection.

**Timeline from run 7's logs (reconstructed from the UUIDv7 request ids in the API log and the
edge access log):** requests arrived at a steady ~300 req/s with no burst. At 19:07:02.65 UTC
completions stopped completely; the edge logged nothing for ~5 s, then a burst of 500–900
responses (half of them 503 after 5.0–5.4 s, the rest successful with `acquired_after_secs`
≈ 5.0), and this repeated every ~5 s until 19:07:47. Only after the first acquire timeouts did
PostgreSQL log the API dropping connections ("could not receive data from client: Connection
reset by peer") and aborted TLS handshakes of replacement connections — a consequence of the
timeouts cancelling in-flight acquires, not the cause. Keycloak was not involved: the stall hit
every route equally, and the OIDC callback failures were simply the sign-ins that happened to be
in flight.

**Root cause (found in code):** pool hold-and-wait, the same class as DEF-P2-CAP-002 / -006, on
the fee spike's hottest student route. `GET /api/v1/finance/me/charges`
(`modules/finance/src/charges/http.rs`, `charge_self_list`) took a pooled connection **first** and
then, while holding it, called `my_accounts` (charges port → pool), `business_today` (reference
port + a pool query) and `charges_of_account` (port → pool) — each of which needs a SECOND pooled
connection. At 15.7 req/s of this route (plus the other fee-spike traffic), as soon as 10
overlapping requests each held one connection and queued for another, the shipped pool of 10 was
deadlocked: nothing could progress until the 5 s acquire timeout failed the queue, which then
re-formed. PostgreSQL saw 10 open, idle connections (checked out but unused), 0 waiters, and the
API used 1 % CPU — exactly the observed signature. The same pattern was in the attendance register
commands (`modules/academic/src/attendance/repo.rs`: start / capture / submit / complete /
finalise opened the transaction and then ran the authorisation, section-context, institution and
roster reads on other pooled connections).

The hypotheses in the brief were checked and **refuted** for this run: the OIDC callback
(`modules/platform/src/auth/http.rs` `oidc_callback` → `issue_session`), the PostgreSQL session
store (`session_pg.rs`), the pre-auth store, the profile sign-in hook, the replay guard and the
`authenticate` / `pre_auth_system` middleware use one pooled statement at a time and hold **no**
connection across the Keycloak token exchange or any other network call; the pool settings
(`SUTRA_DB_MAX_CONNECTIONS=10`, acquire timeout 5 s) are the shipped defaults and were not the
cause — raising them only makes the deadlock rarer.

**Fix (`018d8766`):**

1. `charge_self_list` resolves accounts, business days and the visible charge list through the
   ports first, and only then takes one connection for the per-charge detail reads (acquire late,
   release early; no connection at all when the student has no charge).
2. Attendance register commands: `prepare_session` (authorisation, section context, institution
   writable rule) and the roster read run **before** the command's transaction;
   `lock_prepared` then locks the row, re-checks the section under the lock and the `If-Match`
   version. `require_complete` takes the pre-read roster instead of reading through the port
   inside the transaction.
3. Regression tests on real PostgreSQL, pool of **2**, acquire timeout 5 s
   (`apps/api/tests/db_p2_capacity.rs`):
   `concurrent_fee_self_service_does_not_deadlock_a_small_pool` (16 concurrent
   `/finance/me/charges` + 8 concurrent `/auth/session`, all 200 well inside one acquire timeout)
   and `concurrent_attendance_registers_do_not_deadlock_a_small_pool` (8 sessions, every register
   step run 8-way concurrently: start → capture → submit → complete → finalise, all 200).
4. `docs/readiness/tools/hold-and-wait-scan.py`: a heuristic scan for the pattern. After the fix
   it lists 93 candidates, all in office / administrative **write** paths (mostly "open a
   transaction, then call `require_institution_writable` or a port"); none is on a student
   self-service route, and the few that the load mix touches (exam marks, finance office) run at
   ≤ 1 req/s there. They are recorded as **DEF-P2-CAP-008 (OPEN, lower risk)**: review and
   restructure each the same way, and add the "one connection per task" debug assertion in
   `sutra_persistence::pool` so a new nested acquire fails CI.

Raising `SUTRA_DB_MAX_CONNECTIONS` was **not** used as the fix and thresholds were not touched.

## Production risks

1. **Keycloak brute-force guard locks out real students who sign in from two devices at once.**
   In run 5, 167 results-day sign-ins were refused with `user_temporarily_disabled` for accounts
   that were signing in at the same moment elsewhere. The realm baseline is
   `bruteForceProtected: true`, `failureFactor 5`, `quickLoginCheckMilliSeconds 1000`,
   `minimumQuickLoginWaitSeconds 60`. A student on a phone and a laptop on results day, or a
   parent and a student sharing one account, can trip the quick-login check and be locked out
   for 60 s or more at the worst moment.
   **Recommendation:** keep brute-force protection; do not weaken the failure count or lockout
   ladder. Do these instead:
   - (a) Before go-live, test on the college staging realm whether concurrent *successful* flows
     count as failures in Keycloak 26.7, using the same concurrent same-account check.
   - (b) If they do, lower `quickLoginCheckMilliSeconds` (for example to 100–200 ms) so only
     machine-speed retries count as "quick". Then keep `realm-production-baseline.json` and
     `deploy/keycloak/check-realm.py` in step, because a security change needs the parity gate.
   - (c) Tell the help desk how to unlock a user, and put lockouts on the monitoring board.
   This config was **not** changed in this stage.
2. **Keycloak is the CPU bottleneck in sign-in spikes** (the run 7 results-spike breach, sign-in
   p95 6.2 s against a 5 s limit; run 8: 5,011 ms at 213 % CPU). It peaked at 247 % / 216 % / 236 % of a 4-vCPU host (runs
   5 / 6 / 7) while the API stayed at or below 58 %. In run 7's results spike k6 drove **73
   password sign-ins per second** (`login.password`, 22,026 in 5 minutes), every visit starting
   with a full OIDC sign-in — the worst case. This is a sizing limit, not an API defect, and it is
   **not** worked around in the harness or the thresholds.
   **Recommended Keycloak sizing / configuration** (Keycloak's own guide, "Concepts for sizing
   CPU and memory resources", https://www.keycloak.org/high-availability/single-cluster/concepts-memory-and-cpu-sizing:
   1 vCPU per 15 password logins/s, CPU scaling linearly, plus 150 % head-room for spikes;
   ~1,250 MB base memory per node; heap = 70 % of the container limit):
   - **CPU:** results-day peak ≈ 73 logins/s → **≈ 5 vCPU of steady Keycloak capacity, with a
     limit of ≈ 12 vCPU** (150 % head-room) — e.g. two Keycloak nodes of 3 vCPU request /
     6 vCPU limit, or one dedicated 6–8 vCPU node if the college accepts a slower spike. The
     runner gave Keycloak ≈ 2.4 cores. Do not CPU-throttle Keycloak (its performance drops
     sharply when throttled) and do not co-host the load generator.
   - **Memory:** keep the 2 GiB container limit as the minimum (heap ≈ 1.4 GiB; run 7 used
     1.4 GiB); raise to 3 GiB per node for 2,000+ concurrent sessions.
   - **Password hashing stays as shipped** (Keycloak 26 default policy; the CPU cost per login is
     the hash). Lowering hash iterations / memory would pass the test by weakening security and is
     **not** recommended.
   - **Reduce full sign-ins instead:** keep the realm SSO session (`ssoSessionIdleTimeout` /
     `ssoSessionMaxLifespan` in `realm-production-baseline.json`) long enough that a student who
     already signed in that day gets a cookie login (no password hash) — the harness deliberately
     signs in from scratch on every visit; stagger the results release by programme / year
     (10–15 min apart) so the peak login rate stays under the measured capacity.
   - **Database:** Keycloak's user sessions are in PostgreSQL; the guide budgets 0.35–0.7 vCPU
     per 100 login/logout/refresh per second — already inside the 8-vCPU server estimate below.
   - **Watch** `keycloak_credentials_password_hashing_validations_total` and the Stage 5 sign-in
     p95 alert to confirm the real login rate on results day.
   Re-measure on the college hardware with a separate load machine.
3. **DEF-P2-CAP-007** (above) is fixed; **DEF-P2-CAP-008** (similar hold-and-wait in office write
   paths) remains open; **DEF-P2-CAP-009** (an office desk refused 403 on every request after a normal
   sign-in in run 8) is open with its cause unverified. Until CAP-008 is closed, a burst of more concurrent office writes of one kind
   than pool connections can stall the API for one acquire timeout (5 s).
4. **Load generator on the same host:** k6 itself used CPU on the runner, so these numbers
   understate what the stack could do on a dedicated server. The college run must use a separate
   load machine.

## To complete on the college server

Prerequisites: the college's server, Ubuntu 22.04/24.04 with Docker, sudo, Node 22, k6 and psql.
It needs the real DNS names (`erp.`, `sso.`, `s3.<college domain>`) and TLS certificates. Use a
**separate** load-generator machine on the same LAN. Do this after DEF-P2-CAP-007 is fixed.

```bash
# on the server, from the release bundle (the same procedure the runner used)
cd sutraerp
export CAP_DIR=/srv/sutra-capacity CAP_OUT=/srv/sutra-capacity-out
bash deploy/capacity/run.sh prepare     # replace the private CA with the college certificates (edge.conf.template)
bash deploy/capacity/run.sh up
bash deploy/capacity/run.sh seed        # 2,000 students; or the college's real import files
# on the load machine (k6 --local-ips needs addresses on its NIC; or drop --local-ips and allow-list it in the flood guard)
bash deploy/capacity/run.sh load
# back on the server
bash deploy/capacity/run.sh report      # exit 0 = every threshold met
bash deploy/capacity/run.sh logs; bash deploy/capacity/run.sh down
python3 docs/readiness/tools/cap-report.py "college=$CAP_OUT" >> docs/readiness/CAPACITY_TEST_REPORT.md
```

**Passes when:**

1. `run.sh report` exits 0, meaning every threshold in `thresholds.json` is met in all three
   phases and for every endpoint, with **no edits** to the file.
2. The seed completes every phase.
3. The API log has no "pool timed out" or 503 during the load.
4. There are no Keycloak `user_temporarily_disabled` events for accounts with no failed password.
5. No container exceeds 80 % of its CPU or memory limit for more than one minute.
6. PostgreSQL shows 0 deadlocks.
7. Record the server's CPU model, vCPU and RAM in the report header, as here.
