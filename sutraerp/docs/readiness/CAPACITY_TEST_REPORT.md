# Capacity test report — 2,000-student college (Part 2 · Stage 5)

> **Every number in this report was measured on a GitHub-hosted runner — NOT college hardware.**
> The runner is a shared 4 vCPU / 15.6 GiB cloud VM. Load generator (k6) and the whole stack ran
> on the **same** host, so the load generator took CPU from the system under test. These figures
> show that the procedure works and where the stack breaks first. They are **not** a statement of
> what a college server can carry. The college-server run is **BLOCKED_EXTERNAL** (no server is
> available); see [To complete on the college server](#to-complete-on-the-college-server).

## Verdict

**Not passed on the runner.** The final measured runs (5, 6 and 7) show:

- **Steady college day: within every threshold** apart from harness 412s on one marks endpoint
  (run 7: 0.01 % errors, read p95 13 ms, sign-in p95 115 ms).
- **Results-day spike: API fine, sign-in marginal.** Read/write p95 stay under 300 ms in every
  run, but the sign-in flow p95 was 3.3 s (run 5), 4.3 s (run 6) and **6.2 s (run 7, over the 5 s
  limit)**. Keycloak is the CPU bottleneck (up to 247 % of a 4-vCPU host).
- **Fee-deadline spike: failed in runs 6 and 7** because the API's database pool stalls
  (5–25 s with no request completing, then a burst of 503 "database unavailable"). This is
  **DEF-P2-CAP-007, open and reproduced in run 7**: a product defect, not a hardware limit.
  CPU, RAM and PostgreSQL all had spare capacity during the stalls.
- Six defects found by this test (DEF-P2-CAP-001…006) are fixed, each with a regression test,
  and are green in SutraERP CI. Run 7 is the first run whose seed completed every phase.

Do not take the college to production on the strength of this report. Two things must happen
first: fix DEF-P2-CAP-007 and get a clean run of this procedure on the college's own server.

## What was run

The production-mode stack ran on one host: edge nginx (TLS, host network) → web nginx → API
(`SUTRA_ENV=production`, pool of 10 connections, the shipped default) → PostgreSQL 18 (TLS,
`pg_stat_statements`), Keycloak 26.7 (`start`, brute-force protection on), Flowable 8, NATS, Valkey
and MinIO (SSE-S3). Secrets came from a private CA and were random for each run.

**Seed (through the API, with real approvals):** Stage 4 imports created departments and programmes,
150 staff, and 2,000 students with guardians. The API provisioned 2,000 identities into Keycloak.
Then came 102 divisions with faculty, 2,000 term registrations plus 6,000 seats, the timetable,
6 weeks of attendance (1,224 sessions, 72,000 records in run 6), fees (2,000 charges, 1,600 counter
payments), 300 opening balances, the end-semester exam with results, an open internal assessment,
and one verified PDF per student.

**Load (`k6/college-day.js`, 21.5 minutes; each VU has its own source address):**

| Phase | Window | Users |
|---|---|---|
| steady | 0–10 min | 60 faculty + 40 office staff + 300 students visiting (sign-in → timetable, attendance, results, fees, documents → sign-out) |
| results | 10–15 min | results-day spike: 500 students signing in for results / grade cards |
| fees | 15–21.5 min | fee-deadline spike: 400 students signing in for accounts / charges / receipts / payment gateway |

Faculty and office staff ran throughout: they took attendance (create → start → mark → submit →
complete → finalise), entered marks, searched the directory, took counter payments and ran
reports.

### DEF-P2-CAP-007 — API database pool stalls under the fee-deadline spike (OPEN)

**Evidence (run 38939308465, artifact `capacity-evidence`):**

- The API log shows two windows in which **no request completed at all**. The first ran from
  load second ~1,015 to ~1,030 and the second from ~1,089 to ~1,110, both in the fees phase.
  At exact 5-second steps, 500–800 requests then failed together with 503 "database unavailable"
  after 5.0 s, which is `SUTRA_DB_ACQUIRE_TIMEOUT_SECS=5`. There were 1,926 × 503 in total and
  2,021 "acquired connection, but time to acquire exceeded slow threshold" warnings. Background
  jobs (`audit_seal`, `idp-sync`) failed with "pool timed out" at the same moments.
- **The system was idle during the stalls.** API CPU was 1 %, PostgreSQL 1 % and Keycloak 0.2 %
  (docker stats). In the PostgreSQL samples, all 10 `sutra_api` connections were open but
  **idle**, not active and not waiting on a lock, with 0 lock waiters.
- So all 10 pooled connections were checked out by API tasks that were not using them. The
  database was not busy, no lock was held, and CPU and RAM were free.

**Run 7 (38947132469, same signature on the Intel runner):** 226 "database unavailable" errors
in the API log (178 of them `session creation failed` and the rest `sign-in hook failed (profile
refresh)` on `GET /api/v1/auth/oidc/callback`), 4 "pool timed out" and 2,478 slow-acquire
warnings. Throughout the fees phase PostgreSQL showed at most 3 active connections, 0 waiting and
0 lock waiters, with the API's 10 connections open but idle. The **OIDC callback** (profile
refresh hook + session creation) is therefore the first path to instrument: it is where the
failures land, though that alone does not prove it holds the extra connection.

**Root cause (established up to the mechanism; the code path is not yet identified):** this is the
same class as DEF-P2-CAP-002 and -006. A request path holds one pooled connection while it waits
for a second. sqlx's pool queue is first-come first-served, so once a backlog forms in a spike,
the connections drift to tasks that hold one and queue for another. When all 10 are held this
way, nothing can progress until the 5 s acquire timeout fails the whole queue. That is the
"freeze, then a burst of 503s" pattern. The fees phase brings new high-rate student routes
(`/finance/me/accounts`, `/charges`, `/receipts`, `/payment-gateway`) on top of sign-ins, which is
why it shows there first. A static review of those handlers, the OIDC callback and session
issuing found no second acquire in the obvious places. The culprit is still to be found.

**Fix plan (next stage):**

1. Find the path. Run the capacity stack with a pool-holder diagnostic: log the route when a
   task acquires while already holding a connection (task-local "holding" flag in
   `sutra_persistence::pool`), or run the fees mix against a pool of 2 in a DB test.
2. Restructure that path so it reads its facts before it takes the connection, as was done for
   CAP-002/006.
3. Add a `db_p2_capacity` regression: N concurrent requests of the route on a pool of 3 must all
   succeed.
4. Defence in depth: give each request at most one connection. A debug assertion in the pool
   wrapper would make every future nested acquire fail CI instead of failing production.

Raising `SUTRA_DB_MAX_CONNECTIONS` would make the stall rarer but would **not** remove it. It
must not be counted as the fix.

## Production risks

1. **Keycloak brute-force guard locks out real students who sign in from two devices at once.**
   In run 5, 167 results-day sign-ins were refused with `user_temporarily_disabled` for accounts
   that were signing in at the same moment elsewhere. The realm baseline is
   `bruteForceProtected: true`, `failureFactor 5`, `quickLoginCheckMilliSeconds 1000`,
   `minimumQuickLoginWaitSeconds 60`. A student on a phone and a laptop on results day, or a
   parent and a student sharing one account, can trip the quick-login check and be locked out
   for 60 s or more at the worst moment.
   **Recommendation:** keep brute-force protection; do not weaken the failure count or lockout
   ladder. Do these instead:
   - (a) Before go-live, test on the college staging realm whether concurrent *successful* flows
     count as failures in Keycloak 26.7, using the same concurrent same-account check.
   - (b) If they do, lower `quickLoginCheckMilliSeconds` (for example to 100–200 ms) so only
     machine-speed retries count as "quick". Then keep `realm-production-baseline.json` and
     `deploy/keycloak/check-realm.py` in step, because a security change needs the parity gate.
   - (c) Tell the help desk how to unlock a user, and put lockouts on the monitoring board.
   This config was **not** changed in this stage.
2. **Keycloak is the CPU bottleneck in sign-in spikes.** It peaked at 247 % (run 5) and 216 %
   (run 6) of a 4-vCPU host, while the API stayed at or below 58 %. Sign-in p95 rose from about
   0.1 s to 3.3–4.3 s in the results spike, close to the 5 s limit. Every visit started with a
   full OIDC sign-in, which is the worst case. On college hardware, give Keycloak dedicated
   cores (≥ 2 vCPU reserved, 2 GiB heap). Keep the 2 GiB container limit used here as the
   minimum. Consider a second Keycloak node for results day. Watch the sign-in p95 alert from
   Stage 5 monitoring.
3. **DEF-P2-CAP-007** (above): until it is fixed, a spike can freeze the API for 5–25 s at a time.
4. **Load generator on the same host:** k6 itself used CPU on the runner, so these numbers
   understate what the stack could do on a dedicated server. The college run must use a separate
   load machine.
