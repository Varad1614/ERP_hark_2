### Route sweep allow-lists (each with its reason)

* **Public** (no session by design): `/health/live`, `/health/ready` (probes); `GET /auth/csrf`, `POST /auth/login`, `POST /auth/mfa/verify`, `POST /auth/mfa/webauthn/{challenge,verify}` (pre-session sign-in steps, protected by the pre-session CSRF token, lockout and ingress limit); `GET /auth/oidc/{start,callback}` (OIDC code flow, state/nonce/PKCE checked); `POST /auth/oidc/backchannel-logout` (signed logout token from the IdP); `POST /auth/logout` (idempotent, ends only the caller's own cookie); `POST /finance/gateway/webhook` (authenticated by the gateway signature, not a session); `GET /platform/modules`, `GET /platform/workspaces[/{key}]` (static navigation metadata, no tenant data).
* **Own session only** (session required, no role permission — they act on the caller's own session / second factors): `GET /auth/session`, `GET /auth/mfa`, TOTP enrol/confirm/delete, `POST /auth/mfa/step-up`, WebAuthn registration/assertion/step-up/credential delete, `GET /auth/sessions`, `POST /auth/sessions/revoke-others`, `DELETE /auth/sessions/{id}`.

No other route is allow-listed. Routes the sweep flagged were fixed in code (role pre-check before the first row read), not allow-listed.

### Already verified (no change needed)

`__Host-` session cookie with `Secure; HttpOnly; SameSite=Strict`; CSRF double-submit on every unsafe request (pre-session token on sign-in paths); logout and OIDC back-channel logout revoke the server session; the BFF keeps no refresh tokens (the API session is independent of the IdP token lifetime).

## Accepted risks

1. **Per-replica lockout counter.** The API's failed-attempt counter (#4) is in process memory, so with *n* API replicas an attacker spread across replicas gets up to *n* × 10 attempts per window. Mitigated by the ingress per-IP rate limit on `/api/v1/auth/*` (#5) and, in production (Keycloak mode), by Keycloak's realm brute-force detection (#6), which owns password checking. A shared (Valkey) counter is a later improvement.
2. **Keycloak role removal does not end live API sessions.** Roles are captured in the API session at sign-in; removing a role (or disabling the user) in Keycloak takes effect at the next sign-in, i.e. at the latest after the 30-minute idle timeout (`SUTRA_SESSION_IDLE_SECS` = 1800) or the 8-hour absolute lifetime (`SUTRA_SESSION_TTL_SECS` = 28800). To cut access immediately an administrator signs the user out in Keycloak (session logout → OIDC back-channel logout revokes the API session) or revokes the API sessions; role removal alone waits for the expiry above.
