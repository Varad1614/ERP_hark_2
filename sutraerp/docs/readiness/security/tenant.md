## Accepted risks

| ID | risk | why accepted now | mitigation plan |
|---|---|---|---|
| SEC-P1-TENANT-AR1 | `sutra.rls_scope = 'system'` is an ordinary session setting: SQL running as the runtime role (e.g. an SQL-injection) could `set_config('sutra.rls_scope','system',false)` or change `sutra.tenant_id` and read across tenants. | All SQL is parameterised (sqlx binds; semgrep/CodeQL in sutraerp-quality); the policy removes the *accidental* id-only leak class, which is the defect. Settings are never derived from client input. | (1) move system work to a separate login role `sutra_system` with its own pool and drop the `rls_scope` branch from the policy for `sutra_app`; (2) or sign the context: `sutra.ctx_sig` = HMAC(tenant, institution, scope, backend pid) verified by a SECURITY DEFINER function holding the key; (3) alert on `set_config('sutra.rls_scope'` in pg_stat_statements. Target: Part 2 hardening. |
| SEC-P1-TENANT-AR2 | Backups / `pg_dump` and DR restore need a role that bypasses RLS (FORCE applies to the owner). | Backups must contain every tenant. | Dedicated `sutra_backup` role with `BYPASSRLS`, LOGIN only from the backup job, no app use; deploy/ci/dr-drill.sh to run as that role; db-integrity flags any `sutra_app` member with BYPASSRLS. |
| SEC-P1-TENANT-AR3 | Two child tables have no `tenant_id` and are scoped only through their parent: `institution.org_type_blueprint_unit_type` (→ org_type_blueprint), `institution.org_restructure_move` (→ org_restructure / org_unit). | Every access path joins the RLS-protected parent; no by-id endpoint reads them alone. | Append-only migration adding `tenant_id` (backfilled from the parent) so `apply_tenant_rls()` covers them. |
| SEC-P1-TENANT-AR4 | Non-tenant platform tables (`platform.idempotency_key`, `pre_auth`, `replay_guard`, `event_receipt`, `search_checkpoint`) are outside RLS. | Infrastructure keyed by server-generated keys; `idempotency_key.scope_key` already includes tenant + subject. | Review with the Part 2 platform hardening. |
