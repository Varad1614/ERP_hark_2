# Runbook: backup, restore and disaster recovery (Batch 9 · 9C)

Contract: `docs/batch9-contracts.md` §11. Scripts: `deploy/backup/` (`sutra-backup.sh`,
`sutra-restore.sh`, `lib.sh`, `roles.sql`), `deploy/flowable/init-db.sh`, drill
`deploy/ci/dr-drill.sh`. Chart: `deploy/helm/sutraerp/templates/data/backup.yaml` (CronJob + PVC),
`backup-scripts.yaml` (generated by `deploy/backup/gen-chart.py`; CI fails when stale).

## Targets

| | Pilot target | Evidence |
|---|---|---|
| RPO | 24 h (nightly backup) | CronJob `sutraerp-backup`, schedule `30 20 * * *` UTC = 02:00 IST |
| RTO | 2 h | measured by every DR drill (`Data platform` CI job summary, kind job) |
| Retention | 14 days on the backup PVC (`backup.retentionDays`) | `find -mtime +14` in `sutra-backup.sh` |

NATS JetStream and Valkey are **not** backed up: PostgreSQL (incl. `platform.outbox`) is the source
of truth; the relay re-publishes and caches refill. OpenSearch is **re-projected** from PostgreSQL
after a restore (`search_rebuild`). Flowable's state lives in its own `flowable` database and is
backed up with the same snapshot run.

## What a backup contains (`sutra-backup/v1`)

`sutra-backup-<env>-<UTC YYYYMMDDTHHMMSSZ>.tar` (or a directory without `--tar`):

* `sutra.dump` — `pg_dump -Fc --no-owner` of the `sutra` database. **ACLs are kept** (no
  `--no-privileges`): the REVOKE / GRANT lines that make `platform.audit_log`,
  `platform.audit_chain_entry` / `audit_anchor` append-only (INSERT + SELECT only; the chain head
  also UPDATE) are part of the dump. `sutra-api migrate` does not re-run old migrations after a
  restore, so a dump without ACLs would silently leave the runtime roles without (or with wrong)
  privileges.
  *Deviation from contract §11 (which says `--no-privileges`), made on purpose for the reason above.*
* `flowable.dump` — same for the `flowable` database (when Flowable is bundled / configured).
* `manifest.json` — `format`, `createdAt`, `environment`, `gitSha`, `migrationVersion`,
  `databases[{name, file, bytes, sha256}]`, `auditHeads[{tenantId, seq, headHash}]`,
  `rowCounts{"<schema>.<table>": n}`. Row counts, audit heads and the migration version are read in
  the **same REPEATABLE READ snapshot** that `pg_dump --snapshot` dumps, so they match the dump even
  while the API keeps writing.

Optional encryption: set `SUTRA_BACKUP_AGE_RECIPIENT` (OpenBao group `backup`) → `<name>.tar.age`.

## Schedule (Kubernetes)

`backup.enabled: true` renders a PVC `sutraerp-backup` (kept on `helm uninstall`) and the CronJob
`sutraerp-backup` (image `backup.image`, default `postgres:18`; ServiceAccount `sutraerp-backup`,
bound to the OpenBao role). It reads `SUTRA_MIGRATION_DATABASE_URL` (schema owner, group `database`)
and `FLOWABLE_DB_PASSWORD` (group `flowable`). Only `backup.target.kind: pvc` is implemented in v1;
`s3` fails the render on purpose (copy the PVC off-cluster with your storage tooling until the S3
upload lands).

Manual run: `kubectl -n sutraerp create job --from=cronjob/sutraerp-backup backup-manual-$(date +%s)`.
List backups: `kubectl -n sutraerp run ls --rm -it --image=postgres:18 --overrides='…mount the PVC…' -- ls -l /backups`.

Outside Kubernetes:

```sh
SUTRA_BACKUP_DATABASE_URL=postgres://sutra:…@db:5432/sutra \
SUTRA_BACKUP_FLOWABLE_DATABASE_URL=postgres://sutra:…@db:5432/flowable \
SUTRA_ENV=production SUTRA_GIT_SHA=<image sha> \
  deploy/backup/sutra-backup.sh --out-dir /backups --tar --retention-days 14
```

Tools: bash, coreutils, PostgreSQL **18** client (`pg_dump` must not be older than the server). No
jq / python (JSON is built and compared inside PostgreSQL).

## Restore (step by step)

1. **Stop writers**: scale the API to 0 (`kubectl -n sutraerp scale deploy/sutraerp-api --replicas=0`)
   and stop Flowable (`… scale deploy/sutraerp-flowable --replicas=0`).
2. **Target server**: an empty PostgreSQL 18 (new volume) or the existing one. The script creates
   missing databases; `pg_restore --clean --if-exists` replaces objects in existing ones.
3. **Flowable login role** (when restoring Flowable): `FLOWABLE_DB_PASSWORD=… deploy/flowable/init-db.sh`
   (or let the chart's `sutraerp-flowable-init-db-r<rev>` Job run).
4. **Restore**:
   ```sh
   SUTRA_BACKUP_DATABASE_URL=postgres://<superuser>@db:5432/sutra \
   SUTRA_DB_RUNTIME_USER=sutra_api SUTRA_DB_RUNTIME_PASSWORD=… SUTRA_ENV=production \
   SUTRA_API_BIN=/usr/local/bin/sutra-api \
     deploy/backup/sutra-restore.sh /backups/sutra-backup-production-<stamp>.tar
   ```
   It prints one `ok` line per step and stops at the first failure:
   checksums → `roles.sql` (cluster roles `sutra_*`, `sutra_app`, `flowable`; needed **before**
   `pg_restore` so the ACLs apply) → `pg_restore` sutra (+ flowable as role `flowable`) →
   `sutra-api migrate` (idempotent; re-provisions the runtime login role) → row counts equal the
   manifest → audit heads equal → append-only audit grants present → search rebuild requested
   (`platform.search_checkpoint.rebuild_requested_at = now()`).
   In Kubernetes, run it from a pod with the scripts ConfigMap mounted (image `postgres:18`) and use
   `--skip-migrate`, then re-run the chart's migrate Job (`helm upgrade --reuse-values`).
5. **Start**: Flowable, then the API. `search_rebuild` re-projects OpenSearch within a few poll
   intervals (`SUTRA_SEARCH_POLL_MS`).
6. **Verify**: `POST /api/v1/platform/audit/chain/verify` → `ok: true` (after 9A), a search returns
   results, an approval opens in Flowable (`GET /flowable-rest/service/runtime/tasks`).
7. Record the drill / incident evidence below.

## DR drill

`deploy/ci/dr-drill.sh` (contract §10.4: `ok <check>` lines, `--dry-run`, idempotent):
seed → search baseline → stop API → backup → **wipe** (compose: drop the `sutra` + `flowable`
databases **and** the `sutra_*` / `flowable` cluster roles, delete the search indices; kind: delete
the postgres StatefulSet + PVC and reinstall the release) → restore → audit grants equal
before/after → API ready (RTO) → login → audit chain verify (`ok (skipped: no 9A)` until the 9A
route exists) → Flowable process-definition count equal → search rebuild document counts equal the
baseline → RTO into `$GITHUB_STEP_SUMMARY`.

CI: `.github/workflows/sutraerp-data.yml` job `Data platform (Flowable · OpenSearch · backup →
restore)` runs it in compose mode on every push (PostgreSQL 18 service, Flowable REST 8.0.0 on host
port 8090, OpenSearch 2.19.1 with the security plugin disabled). The kind job (9B) calls it with
`SUTRA_CI_MODE=kind` (`SUTRA_CI_PG_PASSWORD` = the OpenBao `POSTGRES_PASSWORD`).
